# ADR-0040：用户确认分类的持久化与失效边界

日期：2026-09-14。状态：接受目标与边界，数据布局由 S4 在集成契约上实现并补充。

## 问题

只在 Renderer 草稿中锁定分类不能保护关闭应用、重新导入或全库整理后的用户决定。分类锁定必须属于当前 V2 工作区，并与源码和分类规则版本绑定。

## 决策

1. 持久化的确认记录至少包含 templateId、categoryId、taxonomyVersion、sourceHash、确认时间与修订版本。真实路径由本地规范映射解析，AI 不能提交任意锁定状态。用户输入的路径与规范分类不一致时保留显式人工选择，不宣称该路径已经语义验证。
2. Renderer 使用命名、Zod 校验的确认/解除确认 API。Main 解析当前工作区并重新检查源码和记录版本；用户对旧快照的确认不得覆盖新源码或新决定。
3. 未变更源码且版本匹配的用户确认优先于后续 AI 提案；AI 可提出冲突复核，但不能直接修改该确认及其路径。分类锁定不妨碍用户明确发起的手动移动、重命名或解除确认。
4. 源码哈希或分类体系语义变化后，保留旧确认的来源记录，显示“需要重新确认”，不得静默沿用为当前正确结论，也不得静默重新分类。
5. 暂存导入的复核状态绑定 stagingVersion 和 sourceId；所有需要复核的纳入项都必须显式处理或跳过后才能最终应用。晚到 AI 响应不得清除用户新确认。
6. 最终应用把纳入条目的确认状态与索引、元数据、暂存应用状态一同写入现有数据库事务；正式文件修改仍依靠备份、操作日志和失败恢复。
7. 文件移动、ID 重映射、删除撤销、便携备份、跨工作区恢复必须保留或明确失效确认记录。新增数据结构必须覆盖所有显式表/列清单，不能只有首次入库写入而在下一次恢复时丢失。
8. 原位升级用后续 migration，不重写 0009。旧 RC5 备份需在完整性验证后对临时副本进行兼容迁移；不得为了 schema 对齐修改用户原备份文件。

## 验收

- 确认 → 关闭 → 重启仍可见；重新请求 AI 的冲突提案不覆盖确认。
- 外部改源码、分类版本变化、窗口中快照过期均触发重新确认或安全拒绝。
- 单份和批次入口均能使用；待复核项不能通过仅填写元数据绕过。
- 移动/重命名和撤销后的模板、题目关联与确认归属正确。
- 全新库、RC5 库升级、RC5 备份恢复、新版本备份往返、不同工作区恢复均有测试。
- 保留完整人工审查能力；无 AI 配置或离线时用户仍能手动整理。

完成状态和最终字段定义必须由实现与测试结果更新，本文不表示已实现。
