# ADR-0030：自包含工作区文件夹与当前目录原地恢复

- 状态：已由 ADR-0031 取代
- 日期：2026-07-27
- 范围：工作区物理布局、数据库边界、已有 V2 数据升级、备份与恢复

## 背景

现有实现把工作区定义为全局 SQLite 中的一条记录：模板源码位于用户选择的外部根目录，
题目、元数据、图片、文件计划和撤销备份位于 Electron `userData`。v2 恢复为了避免覆盖
外部源码，会要求选择父目录、创建新的模板根并把当前工作区 `root_path` 改到新目录。
因此原文件夹不是完整工作区；恢复后重新选择原文件夹还会被登记为新的空工作区。

产品现在采用更强的物理边界：工作区本身就是一个可复制、可移动、可恢复的文件夹，
文件夹内保存该工作区的全部权威业务数据。备份来源身份不决定恢复目标，恢复永远替换
当前打开工作区的受管内容，且不得改变目标文件夹路径。

## 决定

1. 新建工作区采用以下布局：

   ```text
   <workspace>/
     workspace.awb.json
     templates/
     problem-assets/images/
     .awb/workspace.sqlite
     .awb/file-plan-backups/
     .awb/restore-preflight-backups/
     .awb/recovery/
     .awb/cache/
   ```

   `templates/` 是模板相对路径的起点；数据库只保存受控相对路径。工作区标记包含格式
   版本、工作区 UUID、名称、创建时间和模板目录，不包含任何绝对路径。

2. 为保护已有 V2 模板目录，已登记的旧工作区和用户明确打开的既有源码目录采用兼容
   布局：容器仍为原目录，`templateDirectory` 可为 `.`，新增的标记、`.awb/` 和
   `problem-assets/` 均位于该目录内。应用不为统一外观静默移动既有源码；新建工作区
   固定使用 `templates/`。两种布局具有相同的自包含、备份和恢复语义。

3. 每个工作区拥有独立的 `.awb/workspace.sqlite`，保存 workspace、templates、
   template_metadata、problems、problem_images、template_problem_relations、
   file_change_plans、file_change_executions 和必要的 migration/app_state。运行时使用可
   切换数据库代理，使现有领域服务在切换后只访问活动工作区数据库。

4. Electron 全局 `algorithm-workbench.sqlite` 只继续作为应用级数据库和工作区登记簿：
   保存 AI Provider、任务路由、活动/最近工作区路径和兼容升级来源。工作区业务表的旧
   数据在成功深拷贝、完整性检查之前不得删除；升级完成后它们不再是运行时事实来源。
   API Key 继续由 OS 安全存储保护，不写入工作区。

5. 打开已有 V2 工作区时，应用先创建一致的工作区数据库临时副本，按工作区过滤旧
   SQLite 行，复制该工作区题目图片和受管文件计划备份，校验 quick_check、外键、数量
   和文件哈希，再原子发布标记与工作区数据。失败时保留旧全局数据和原模板目录，不
   发布半个工作区。未登记的已有源码目录必须经过用户确认后才初始化受管文件。

6. 工作区登记通过标记 UUID 和当前规范化路径共同解析。相同 UUID 的旧路径不可用时
   视为工作区移动；旧路径仍可用时视为副本，必须为副本分配新的目标身份或由用户
   明确选择，不能让两个打开位置共享可变身份。路径变化不能使题目和元数据消失。

7. `.awb-backup v2` 继续使用 UTF-8/EFS、NFC、原始源码字节和严格路径校验。导出只
   包含当前工作区的一致 SQLite 快照、模板树、题目图片和受管撤销备份；排除 Provider、
   密钥、全局设置、cache、lock、WAL、SHM 和临时恢复目录。包内绝对路径和来源身份不
   具有恢复权限。

8. 普通恢复不再选择父目录或创建新的工作区根。目标由 Main 在确认时重新解析为当前
   工作区；目标路径、名称和 UUID 保持不变。恢复先校验包并创建当前工作区完整预备份，
   再在应用控制的暂存位置重映射内部引用、构建目标模板树和工作区数据库。提交时原子
   替换当前工作区受管内容；失败或中断必须回滚。暂存目录是实现细节，不能成为新的
   工作区或出现在用户恢复流程中。

9. 恢复是替换，不是合并。备份中不存在的旧模板、题目、图片、计划和执行从活动数据
   中移除，但保留在操作前备份中。未受应用管理的文件不得静默删除或覆盖；路径冲突
   必须在写入前报告。恢复后重新打开、切换离开再切回以及重启应用，必须从同一目标
   文件夹得到相同数据。

10. Renderer 仍不接触文件系统、SQLite 或任意路径。Preload 删除“选择模板恢复父目录”
    能力；恢复 IPC 不再接受 `templateRestoreRoot`/`templateSourceStrategy`，只接受已
    预览的包、来源摘要、目标工作区身份、请求 ID 和显式确认。Main 在提交前再次验证
    活动工作区、标记、数据库和模板版本。

## 数据保护与兼容

- 全新安装创建自包含空白工作区，不需要旧项目或全局业务数据库。
- 已有 V2 数据采用复制、校验、发布三阶段升级；原全局业务行作为兼容恢复来源保留，
  不允许通过删除旧数据库完成迁移。
- 工作区数据库使用 SQLite backup API 生成一致快照，不直接复制活动 WAL/SHM。
- 模板源码、图片和撤销备份按原始字节复制并做 SHA-256 校验；中文路径继续执行 NFC、
  Windows 非法名和大小写碰撞检查。
- 工作区切换前取消并等待当前工作区后台任务与 AI 文件任务，关闭旧 SQLite 后再打开
  新数据库，避免跨工作区迟到写入。

## 验收

- 新建工作区在所选文件夹内形成标记、`templates/`、题目附件和独立 SQLite。
- 已有 V2 工作区升级后，清空全局业务查询仍能从工作区文件夹读取模板、元数据、题目、
  图片、关联、计划和执行；Provider 配置保持全局。
- A 备份可恢复到任意当前 B；恢复 UI 不出现父目录选择，B 的路径/名称/UUID 不变。
- B 恢复后切到 C、再选择 B，以及应用重启后，数量、内容、关系和文件哈希保持一致。
- 恢复失败、外部文件冲突、磁盘写入失败和模拟中断均不留下半提交状态。
- macOS 与 Windows 对中文/组合字符、GB18030/GBK/CP936、UTF-8/UTF-16 源码和大小写
  冲突执行相同规则；平台 runner 与真实 Windows 往返证据分别报告。

## 后果

- 工作区可以直接复制到另一台机器后打开；备份包仍提供校验、目标重映射和事务恢复。
- 动态工作区数据库会扩大初始化、切换、测试夹具和发布 smoke 的覆盖范围，但消除了
  全局业务库与外部源码目录之间的双重事实来源。
- 兼容工作区可能以 `.` 作为模板目录；这是保护既有源码路径的有意取舍，新建工作区
  始终使用清晰的 `templates/` 容器结构。
