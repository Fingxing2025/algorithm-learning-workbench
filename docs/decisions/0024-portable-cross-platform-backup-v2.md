# ADR-0024：跨平台可移植备份 v2

> 兼容读取旧 v1 目录包的部分已由 ADR-0031 取代；当前应用只接受单文件 v2。

- 状态：接受；第 8–10 条恢复目标规则已被 ADR-0030 取代
- 日期：2026-07-23
- 范围：macOS 与 Windows 之间的数据备份、校验和恢复

## 背景

现有 `.awb-backup v1` 是一个目录包。它适合当前机器上的一致性快照、篡改检测和事务式恢复，但在 Finder、资源管理器、网盘和移动介质之间传输时容易被误当成普通目录；用户手工压缩后，ZIP 文件名编码、路径分隔符和 Unicode 归一化由外部工具决定。v1 恢复还固定跳过模板源码，并保留备份数据库中的原工作区绝对路径，因此不能作为 macOS 与 Windows 之间的完整迁移闭环。

跨系统闭环必须同时保护三类事实：

1. 数据库、题目图片、文件操作备份和模板源码的字节不能被转码或静默改名。
2. 备份中的路径在大小写不敏感文件系统和 Windows 路径规则下不能产生碰撞、越界或设备名冲突。
3. 恢复必须先验证、先创建当前状态预备份，并且模板源码只能写入用户选择的全新目录；不能覆盖目标系统已有工作区。

## 决定

> 2026-07-27 更新：本 ADR 的 ZIP、编码、路径和完整性规则继续有效；第 8–10 条所述
> “另选父目录并创建新根”仅记录当时方案。当前恢复必须按 ADR-0030 原地替换活动的
> 自包含工作区，不改变目标路径、名称或 UUID。

1. 外部导出默认升级为单文件 `.awb-backup v2` ZIP；ZIP entry 名使用 UTF-8/EFS、`/` 分隔符和 NFC。v1 目录包继续只读验证和恢复，内部恢复预备份暂时保留 v1 目录格式，避免改变既有生命周期与异常恢复协议。
2. v2 manifest 继续保留 v1 的通用字段，并新增可移植性声明与工作区源码摘要。它明确记录 ZIP、UTF-8、NFC、大小写碰撞检查、Windows 路径检查和源码字节保持策略；不记录原工作区绝对路径。
3. 备份构建使用纯 JavaScript 流式 ZIP 读写，不调用系统 `zip`、`unzip`、PowerShell 或 shell。新增 `yazl` 与 `yauzl`：二者为 MIT 许可、无原生构建，职责不重叠；前者只写，后者只做懒加载校验与解包。
4. 所有 v2 entry 在发布前执行可移植路径预检：拒绝绝对路径、反斜杠、`.`/`..`、NUL/控制字符、Windows 非法字符、尾随空格或点、保留设备名、过长段；路径必须已是 NFC。使用“NFC + 不区分大小写”键拒绝重复和碰撞，不自动重命名。
5. v2 验证严格枚举中央目录：拒绝加密 entry、目录/符号链接、重复路径、清单外文件、清单缺失、Zip Slip、无法解码名称、条目/总展开大小超限和异常压缩比。解包到应用创建的临时目录后，再复用 manifest、SHA-256、SQLite `quick_check`、外键和 Provider 密钥引用检查；无论成功失败都清理临时目录。
6. 源码按原始字节复制和压缩，不添加 BOM，不猜测或转换 GBK/CP936，不自动转换换行或 Unicode 内容。SHA-256 用于证明传输前后字节一致；恢复后的文本读取由第 13 条统一源码编解码层负责。
7. v2 通用备份强制包含模板源码、相对路径和工作区业务数据。普通 UI 不再提供关闭源码的选项；历史上省略源码的 v2 包可以识别但不属于可恢复的通用深拷贝包。
8. v2 恢复时用户必须选择一个父目录；Main 在其中规划一个尚不存在的新恢复根目录。目标存在、符号链接、路径不便携或任何文件冲突时，在修改当前 userData 前失败。
9. 模板源码先写入全新的目标根并按备份哈希验证。包内工作区 ID/名称只作溯源，恢复目标始终是执行时的当前工作区。Main 在应用拥有的临时包副本中，把 workspace、模板、题目、图片、计划、执行主键及计划/执行 JSON、图片目录和执行备份目录引用一致重映射到目标作用域，再进入既有 userData 目录交换和 SQLite 恢复。
10. 当前目标工作区保留自己的 ID、名称和应用身份，`root_path` 指向新恢复根；来源及其他工作区和 Provider 不变。事务失败时回滚 userData 并尽力删除本次新建的恢复根；绝不修改原备份包、来源目录或恢复前已存在的外部目录。v1 仅保留内部预备份和高级兼容用途，不具备新 v2 的通用深拷贝保证。
11. 恢复前预备份、目录交换、SQLite 提交标记、失败回滚和异常中断人工恢复继续沿用 ADR-0015。v2 不改变数据库 schema，不把 ZIP entry 直接写入 Renderer，也不开放任意路径或原始 IPC。
12. 自动化必须覆盖中文/组合字符、大小写碰撞、Windows 设备名、Zip Slip、清单外 entry、篡改、v1 兼容、v2 单文件导出、源码恢复到新根、工作区路径重映射和失败零覆盖。macOS 测试与 Windows CI 都通过后，仍需真实 Windows 主机完成“macOS 导出 -> Windows 校验/恢复 -> 重启读取 -> Windows 再导出 -> macOS 校验/恢复”的往返验收，才能宣称实机闭环完成。
13. 模板源码文本采用统一的严格解码层：先识别带 BOM 的 UTF-8、UTF-16LE/UTF-16BE，再尝试严格 UTF-8，最后依次尝试 Windows 中文环境常见的 GB18030 与 GBK/CP936，并要求解码后回编码字节完全一致；少数 CP936 扩展字节必须保持为 GBK/CP936，不能在编辑时悄悄改写成不同的 GB18030 字节。扫描、源码查看、单份/批量导入、相似度审计和 AI 源码片段必须复用同一解码器，禁止用宽松 `Buffer.toString('utf8')` 产生替换字符。现有工作区文件在应用内编辑时保持检测到的原编码和 BOM；无法无损回编码时拒绝保存。应用新建的文件和从外部导入后创建的新副本仍统一写为 UTF-8，且必须在界面标明检测到的源编码；外部原文件与备份中的源码字节始终保持不变。中文传统编码由 MIT 许可、纯 JavaScript、无原生构建影响的 `iconv-lite` 提供。

## 后果

- 用户得到可直接复制的单文件备份，不再需要手工压缩 v1 目录。
- 路径不便携时导出会明确失败；应用不会为追求成功率而悄悄改名或转码用户文件。
- ZIP 校验需要临时展开空间，导出也会短暂同时占用 staging 目录与 ZIP；后续可增加磁盘空间预估，但不能放松完整校验。
- v1 仍可恢复，已有恢复预备份和生命周期清理记录不迁移、不重写。
- 自动化只能证明代码级跨平台契约；没有真实 Windows 往返证据时，交付报告必须把“已实现/CI 验证”和“实机闭环”分开。
- GB18030 支持需要纯 JavaScript 编解码表，但不引入原生模块；编码识别只接受严格、可回编码的文本，不能把任意二进制文件猜成 Windows 中文源码。
