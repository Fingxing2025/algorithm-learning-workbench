# 0015：V2 数据备份、诊断与恢复

## 背景

V2 已经把工作区索引、模板元数据、题目、图片、模板题目关系、AI Provider 非密钥配置、任务路由、文件计划和执行记录保存到应用数据目录。模板源码仍属于用户选择的外部工作区。下一阶段必须让这些数据可以被只读诊断、可验证导出，并为后续原子恢复提供稳定契约。

## 决定

1. 备份包采用版本化目录包，首版格式版本为 `v1`，最终产物扩展名为 `.awb-backup`。包内必须包含 `manifest.json`、`checksums.sha256`、`COMPLETED` 和 `data/` 目录。后续应用只能读取声明为兼容的 manifest 主版本；不兼容版本必须在预览阶段给出可操作错误，不进入恢复。
2. `manifest.json` 是唯一的结构化清单，使用 Zod 校验。它记录应用版本、格式版本、创建时间、数据摘要、文件清单、每个文件的字节数和 SHA-256、是否包含模板源码、Provider 密钥缺失标记、SQLite 快照状态、诊断摘要和隐私排除项。`checksums.sha256` 是给人工审计和篡改检测用的冗余清单，必须与 manifest 中的文件哈希一致。
3. SQLite 导出必须使用一致性快照。Main 进程对当前连接执行 `wal_checkpoint(PASSIVE)` 后，用 SQLite `backup()` API 或等价在线备份复制到临时目录，再对快照运行 `PRAGMA quick_check` 与 `PRAGMA foreign_key_check`。导出包不直接复制活动的 `.sqlite-wal` 和 `.sqlite-shm`。
4. 导出只包含受控用户数据：SQLite 快照、题目图片、文件计划备份、批量覆盖备份，以及可选模板源码副本。Electron 缓存、Session Storage、Local Storage、Cookies、GPU/Code Cache、`secrets/` 和安全存储密钥文件默认且首版固定排除。
5. Provider 只导出非密钥配置和任务路由。SQLite 快照中不得保留 `secret_ref` 原值；导出快照必须把 `ai_provider_profiles.secret_ref` 置空，并在 manifest 标记 `providerSecrets: "omitted"` 与恢复后需要重新填写密钥。
6. 模板源码默认不纳入备份。导出请求必须包含用户明确选择的 `includeTemplateSources` 布尔值；为 `true` 时只复制当前 V2 工作区根目录内的普通模板文件，跳过符号链接、目录穿越和超出工作区授权范围的路径。恢复模板源码时不得静默覆盖现有外部工作区，必须提供跳过、恢复到新目录或用户确认覆盖策略。
7. 所有导出先写入同目录下带随机后缀的临时包目录，生成 manifest、校验和和 `COMPLETED` 后执行全包验证。验证通过后用原子 `rename` 发布最终 `.awb-backup`；若目标已存在则失败并要求用户选择新路径。失败必须清理临时目录，不留下看似完整的备份包。
8. 恢复前必须只读校验完整包：检查 `COMPLETED`、manifest 版本、清单覆盖、大小、SHA-256、SQLite quick_check、外键、Provider 密钥缺失、模板源码策略和潜在冲突。用户确认前不得修改当前 userData 或模板工作区。
9. 恢复执行前必须自动备份当前状态到 `restore-preflight-backups/`，并用与普通导出相同的校验规则验证。恢复使用临时目录和原子替换，任一步失败都要恢复到操作前状态。首个纵向切片若不能完整验证恢复路径，Renderer 不暴露可执行恢复入口，只提供只读验证和预览。
10. 诊断默认只读，覆盖 SQLite、图片与记录对应关系、模板/题目/关系/文件计划计数、Provider 非密钥配置、任务路由、`file-plan-backups/`、`batch-import-backups/`、孤立图片、残留 `.trash`、临时文件、无记录备份和空间统计。未经用户明确确认，不删除、移动、覆盖或修复任何用户文件。
11. 日志、错误信息、诊断 JSON 和截图不得包含题面、用户笔记、模板源码、API Key、密钥引用文件名或不必要的绝对路径。导出/诊断只报告计数、相对路径类别、大小、哈希和问题代码；UI 可显示用户主动选择的目标文件名，但不把完整隐私路径写入诊断产物。
12. 备份保留和清理首版只做统计与边界识别：报告 `file-plan-backups/`、`batch-import-backups/`、未完成临时包和恢复预备份占用，不自动清理。后续清理必须单独提供确认 UI，并限制在应用自建备份目录内。
13. 备份生命周期治理默认采用“永久保留”，也允许用户在数据管理页临时选择 7、30 或 90 天策略。策略只决定哪些恢复预备份被列为建议清理项，不启动后台任务，也不自动删除；无论策略如何，最新一份已完成且验证通过的恢复预备份始终受保护。
14. Main 进程负责生成清理清单。Renderer 只能接收不含绝对路径的候选摘要，并提交 Main 生成的不透明候选 ID；不得提交原始路径。执行前 Main 必须重新扫描并核对候选 ID、规范化路径、根目录边界、符号链接、类型、大小和修改时间，状态变化、伪造 ID、路径越界或符号链接一律拒绝整批操作。
15. 可治理范围固定为应用 `userData` 内的 `restore-preflight-backups/`、`file-plan-backups/`、`batch-import-backups/` 和 `problem-images/.trash/`。仍可撤销的文件计划备份、最新有效恢复预备份、活动 SQLite、题目图片正文、密钥目录、Electron 数据目录、外部导出包和外部模板工作区均不可进入清理候选。`.restore-*.tmp`、未完成隔离目录和无法证明安全的异常项只报告为需要人工检查，不允许从首版清理入口移动。
16. 清理不直接永久删除。用户先查看逐项预览和预计移动空间，再勾选明确确认；Main 随后把全部选中项通过同文件系统原子 `rename` 移入 `data-management-quarantine/<operation-id>/`。隔离清单格式为 `v1`，记录操作 ID、创建时间、候选类别、原受控相对路径、字节数和扫描指纹，并以 `manifest.json` 与 `COMPLETED` 标记完成。首版不提供清空隔离区或不可撤销删除入口。
17. 批量隔离和撤销采用全有或全无语义。任一步失败时，已移动项按逆序回到原位；撤销前必须确认所有原位置仍为空且仍在允许根目录内，失败时不得覆盖后续产生的文件。故障注入必须覆盖中途失败回滚。异常退出遗留的 `.cleanup-*.tmp` 只读报告并受保护，后续不得将其当作普通临时文件删除。
18. `file-plan-backups/` 中仍对应 `applied` 执行记录的目录受保护；对应 `rolled-back` 记录但仍残留的目录可建议清理；无执行记录的目录和 `batch-import-backups/` 仅作为需要用户判断的候选。应用只报告问题图片 `.trash` 中无当前数据库引用的残留项。所有列表、错误和测试证据只使用类别、时间、大小、数量和短候选标识，不输出题面、源码、笔记、密钥或不必要的绝对路径。

## 后果

- 目录包比 zip 更容易在不增加压缩依赖的情况下实现原子发布、逐文件校验和故障注入测试；压缩格式可在 `v2` 中加入，但不得破坏 `v1` 读取。
- SQLite 快照会短暂增加磁盘占用，导出前需要检查并报告估算空间。
- 导出的 Provider 配置可恢复任务路由和非密钥参数，但用户必须重新输入 API Key。
- 只读诊断可以先交付并覆盖真实用户数据风险；原子恢复必须等导出、校验和预览都稳定后再打开执行入口。
- 隔离而非永久删除会让磁盘空间暂时仍被应用占用，但换取可撤销和故障回滚能力；永久清空需要后续独立决策和二次确认流程。
- 保留策略不持久化且不自动执行，避免用户误以为应用会在后台静默删除备份；每次清理都必须重新选择、预览并确认。
