# ADR-0028：所有批量任务展示真实进度

## 背景

工作区扫描和只读审计已经通过 Main 内存后台任务展示完成数，但批量模板导入、已有模板元数据补全、总体文件 AI 计划、文件计划执行以及备份与恢复仍主要依赖按钮转圈或笼统文案。用户无法判断任务正在等待 Provider、处理哪一项，或已经完成多少项，也难以区分正常等待与超时。

这些任务跨越 Renderer、Preload、IPC、Main 文件系统和 Provider 请求。进度信息本身也必须遵守隐私与路径授权边界，不能为了展示状态把绝对路径、源码、题面、用户笔记或密钥送回 Renderer。

## 决定

1. 所有用户主动发起、一次处理多项或可能持续等待的任务，至少展示当前阶段；能获得真实逐项计数时同时展示“已完成 / 总数”和当前项。瞬时 SQLite 单事务写入不伪造逐项百分比。
2. 复用 Main 的 `BackgroundTaskRegistry` 作为统一内存进度源。除原有可取消后台任务外，它允许 IPC 在保留原返回值的同时登记一个可轮询的受跟踪操作；Renderer 使用请求 UUID 轮询命名 `backgroundTasks.get` API。
3. 统一进度包含阶段、已完成数、可空总数和可空当前项。阶段使用受控枚举；当前项只能是模板显示名、受控工作区相对路径或不含用户数据的动作标签，最长 500 字符。
4. 逐项任务在每项开始与完成时更新；批量文件写入按“校验 → 备份 → 写入 → 重建索引 → 发布”更新。Provider 单次请求无法提供真实百分比时，只展示“等待 Provider 响应”和已等待时间，不推测 Token 或模型完成比例。
5. 取消沿用现有任务控制：取消后状态进入 `cancelling/cancelled`，迟到 AI 响应不得写入草稿或计划。不可安全中断的事务式文件任务只展示进度，不在提交中途新增取消入口。
6. Renderer 使用统一的无障碍进度组件，包含 `role="status"`、`aria-live="polite"`、阶段文案、真实计数、当前项和已等待时间；亮色、深色和紧凑窗口都必须可见。
7. 任务状态只驻留 Main 内存，不新增数据库表、migration、备份格式或 Provider 协议。应用退出时继续取消并等待所有活动任务后再关闭数据库。

## 后果

- 用户可以区分本地准备、Provider 等待、逐项处理、文件写入、校验和发布阶段，并看到可验证的真实计数。
- 原有业务 IPC 仍返回原结果；新增的请求 UUID 只用于进度关联，避免把大型结果复制到后台任务状态中。
- 进度轮询是短期本地 IPC，任务结束后由现有上限清理；应用重启后不恢复进度。
- 对无法观测内部百分比的第三方 Provider 只提供阶段与等待时间，避免虚假精度。
