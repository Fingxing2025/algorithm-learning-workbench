# ADR-0029：批量 AI 请求使用输入预算、确定性分批与全局合并

- 状态：已接受
- 日期：2026-07-24
- 更新：2026-07-25（增加输出感知分批、批次超时诊断、结构/语言失败自适应拆分）
- 范围：总体文件 AI、批量模板分类和已有模板元数据补全

## 背景

总体文件 AI 曾允许把完整目录、全量审计、候选元数据和源码片段组合成单次约 96,000 Token 的输入。第一轮改为约 32,000 Token 输入分批后，真实 38 模板工作区仍出现超时：31 个缺少元数据的候选输入总量不大，因而仍进入同一批，而该批允许输出 16,384 Token。OpenAI Chat Completions 兼容 Adapter 会等待完整响应，模型可能在 120 秒内无法一次生成大量完整操作。这证明只按输入字符装箱不足以控制生成延迟，还必须约束单批候选数和输出预算。

已有模板元数据补全和批量模板分类虽然逐模板调用 Provider，但单份源码仍可能携带最多 120,000 字符，也需要统一的单次输入上限。

进度展示只能让等待可见，不能降低单次请求体、首字延迟或超时概率，因此必须同时约束每次网络调用的输入规模。

## 决定

1. Main 必须先完成当前工作区的本地全量盘点、只读审计和发送快照，再决定网络批次；Renderer 不负责拆分 Provider 输入。
2. 已有模板元数据补全和批量模板分类继续采用约 32,000 个估算输入 Token 的单次安全预算。总体文件 AI 使用更保守的 24,000 Token 单批预算，并要求完整目录上下文先适配 16,000 Token。预算覆盖稳定目录、system prompt、JSON Schema、当前批次 payload 和固定协议开销；不得只计算源码字符。
3. 总体文件 AI 把审计问题按共享路径组成确定性连通分组，再按输入预算、详细候选数量和审计问题数量顺序装箱。常规每批最多 4 个详细候选、6 个审计问题；共享同一模板的审计问题必须位于同一批，即使该不可拆分组件超过常规数量上限也不能拆开。每批只携带当前分组相关的审计问题、候选元数据和源码。
4. 每个总体文件 AI 批次仍必须携带完整的最小工作区 catalog：分级目录树，以及每份模板的稳定 ID、名称、工作区相对路径和语言。可选摘要、附加元数据、相关候选和源码可以按预算缩减；最小完整 catalog 本身超过单批预算时，在任何网络请求前返回 `AI_CONTEXT_TOO_LARGE`，不得退回局部目录。
5. 源码缩减使用显式标记的头尾保留策略，payload 同时说明原始字符数、是否截断和截断策略。禁止无标记地只取开头。已有模板元数据补全和逐份模板分类复用同一输入预算和源码缩减规则。
6. 总体文件 AI 的单批输出上限固定为 4,096 Token；Provider 明确拒绝该上限时统一 Adapter 仍可降到 2,048 Token。system prompt 同时要求 summary 不超过 300 字，每项 evidence 和 alternatives 只保留最关键的 1–3 条，避免输出内容重复输入。
7. 总体文件 AI 依次发送所有锁定批次，并向统一后台任务进度报告“第 x / y 批”、当前候选和已完成批次数。单个 Provider 请求内部仍不伪造 Token 百分比。
8. Main 逐批拒绝当前批次之外的模板操作，只在全部批次成功后合并结果。合并后统一检查未知模板、同模板重复操作、跨批目标路径冲突、必需改名覆盖、文件前置条件和 100 项操作上限。任一批失败、取消或全局校验失败时，整次生成失败，不创建部分计划，也不修改文件。
9. 连接超时、响应超时和流中断的可操作错误必须包含第 `x/y` 批、该批估算输入 Token、候选数、4,096 Token 输出上限和已完成批数；安全诊断只记录批次序号、计数、Token 估算和错误码，不记录路径、源码、笔记或密钥，并保留原错误的 `retryAfterMs` 与阶段。
10. 普通 JSON 模式下，某批的首次生成和一次结构修复仍无法通过 JSON/Schema 校验时，Main 只对这个失败批次按既有审计连通分组进行二分，并顺序重试子批次；已成功的基础批次不重新发送。中文/英文语言校验在每批首次得到结构有效结果后执行：首次违规只语义重试当前批；修正请求若返回坏 JSON、网络错误或仍不合规，必须回退到修正前的结构有效结果进入用户审查，并在合并计划摘要中标出对应批次，不得把最佳努力的语言修正失败重新分类为结构失败。常规四候选批次的首次结构失败最坏拆到单候选，最多进行 7 次拆分；共享路径的重复/相似审计连通组仍不可拆。网络超时、流中断、鉴权、限流、模型和路径越界、跨批操作等其他业务错误不触发该机制，避免不确定的重复计费或降低安全校验。
11. 自适应子批次必须继续携带同一锁定快照中的完整 catalog，并只能返回该子批次的模板操作。进度保持基础批次 `x/y` 不倒退，同时显示“自适应子批 1/2”等当前项；安全诊断只增加拆分次数、子批候选数、输入 Token、深度和已完成子批数。拆分结果只驻留内存，全部基础批次及全局校验成功前仍不得创建计划。
12. 用户只审查和确认一份合并后的计划。计划执行、逐项选择、二次确认、操作前备份、事务式补偿回滚和撤销前冲突检查保持不变。
13. 预览必须显示预计基础请求批数、常规单批候选上限、单批输出上限、单批最大输入和全部基础批次总输入；一次性 `previewId`、五分钟 TTL、输入哈希、Provider/模型指纹和发送前文件复检继续覆盖全部批次。自适应子批次是锁定基础批次的确定性子集，不重新读取或扩大发送内容。
14. 文件 AI Provider 是否使用原生结构化输出仍由现有 Provider 能力配置决定。本决定不改变已确认的兼容策略：文件管理可关闭“结构化输出”并继续使用本地 JSON 提取、Zod 校验和 Main 业务校验；题目分析可以使用另一份开启结构化输出的 Provider 配置。
15. 语言字段按是否会进入模板数据区分：元数据自然语言说明在中文模式下应含中文，但 `DP`、`Bitmask DP`、`C++17` 等惯用技术短语和 `n <= 20` 等约束公式合法；标签允许中文或惯用算法/编程专名（例如 `Segment Tree`、`Fenwick Tree`、`Lambda`、`String`、`C++`）；目标路径应使用中文或惯用技术专名。summary、reason、evidence、applicability 和 alternatives 继续由提示词要求使用目标语言。语言一致性属于可审查的内容质量要求，不是路径授权、覆盖、冲突或数据保护边界；一次自动修正后仍不一致时以计划摘要警告代替失败，最终执行仍须用户逐项确认。
16. 计划安全诊断以向后兼容的默认字段记录基础批数、有效批数、自适应拆分数和语言回退批数。旧计划缺少这些字段时解析为 `0`；这只扩展版本化 JSON 诊断，不改变 SQLite 表结构、执行协议或备份格式。

## 后果

- 大批量任务的总耗时可能增加，但单次请求显著变小，首字延迟和单次超时风险降低，失败位置也能通过批次进度定位。
- 完整 catalog 会在每批重复发送；支持 Prompt 缓存的 Provider 可以复用稳定前缀，不支持时会增加输入计费。预览必须明确展示总输入估算。
- 只有普通 JSON 的结构提取/Schema 校验连续失败时才增加子批请求；这会增加该失败批次的耗时和输入计费，但比重新运行全部基础批次更小，并能把输出规模自动降到单候选。
- 单批语言违规只会重试当前批一次；仍违规时保留结构有效结果供用户审查，不再拆分或重新计费前面的成功批次。只有 JSON/Schema 结构失败进入自适应拆分。
- 估算 Token 仍不是 Provider 官方 tokenizer 的精确结果，因此 24,000 输入、4 个常规候选和 4,096 输出是保守客户端预算，不是绝对的超时保证。Provider 自身限流、网络中断和模型拥塞仍可能失败。
- 任一批失败都不产生半份草稿，用户数据保护语义不因分批而降低。
