# 0012：版本化工作区 AI 上下文与结构化题目分析

## 背景

模板入库原本只根据当前源码生成路径，不知道整个工作区的分类习惯；题目 AI 分析也只使用模板名称、路径和语言做推荐。重复发送工作区上下文会增加成本，但把所有功能放入一个长期对话会导致任务指令污染、过期上下文和跨 Provider 不兼容。

## 决定

1. Main 根据当前工作区的路径、修改时间、元数据和关联统计生成不可变的 `WorkspaceAiContext`，并使用 SHA-256 生成版本。
2. 上下文分为全局目录分类摘要和按当前任务本地检索的相关模板；不将整个工作区所有完整源码无条件上传。
3. 模板路径补全优先选择现有目录，只在必要时建议新建子目录；分类链允许 2–5 级。模型返回放置方式、依据、置信度和备选位置，最终路径仍由本地组合和校验。
4. 模板补全接收用户已填写草稿，模型只补空字段；用户笔记不发送给模型。模型违反约束时仍进入逐字段冲突审查。
5. 题目原文与 AI 摘要分离。`problems.statement` 继续作为原始题面字段，新增 `ai_summary` 与 `analysis_json`；旧题目原地升级后摘要为空、结构化分析为空对象。
6. 题目分析输出包含输入说明、输出说明、约束、样例、算法信号和边界情况；模板候选包含证据、适用条件、不适用条件、匹配能力与警告。
7. 两类任务都在请求前展示 Provider、模型、输出语言、要发送的文件/图片/上下文范围、截断状态、粗略 Token 估算和缓存键。用户确认前不发送网络请求。
8. AI 输出统一经过 JSON 提取、Zod 校验和一次受限格式修复。鉴权、模型不存在和能力不支持不重试；限流、短暂网络与 5xx 只做有上限的重试。
9. 不创建跨功能长期对话。每个 Provider Adapter 可根据显式能力复用稳定的工作区上下文前缀；缓存键至少包含工作区、Provider、模型、上下文版本、Prompt Schema 版本和输出语言。
10. 上下文缓存只是成本/延迟优化。本地索引、安全校验、草稿确认和数据回滚不依赖 Provider 缓存。
11. OpenAI 原生严格结构化输出使用全字段 `required` 且禁止额外字段的 Schema 副本，不改变本地 Zod 契约。若兼容端点以 HTTP 400 明确拒绝原生结构化参数，同一任务只降级为一次“Schema 写入 Prompt + 本地严格校验”；不降级最终校验，不重试鉴权或模型不存在错误。
12. 模板补全语言切换时，Renderer 撤回上一轮仍未被用户修改的 AI 生成字段，再按新语言生成；用户原始字段和后续手动修改始终保留。Main 只对 AI 新补全的字段执行输出语言校验，不因用户已填内容使用其他语言而拒绝整个结果。

## 后果

- 新增的题目字段需要版本化 migration，不允许删库重建。
- 工作区变化会产生新上下文版本；旧 Provider 缓存不再引用，等待供应商 TTL 到期。
- 大型工作区发送压缩分类摘要和相关模板，界面必须显示截断与选取数量。
- 不支持 Prompt Cache 或 Structured Output 的自定义 Provider 会退化到普通文本请求和本地严格校验。
