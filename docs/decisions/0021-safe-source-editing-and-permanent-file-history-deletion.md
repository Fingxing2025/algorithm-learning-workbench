# ADR-0021：模板源码安全编辑与文件历史永久删除

- 状态：已接受
- 日期：2026-07-22
- 范围：Session G 用户功能
- 替代：ADR-0017 第 6–7 条、ADR-0019 第 5–10 条

## 背景

模板源码当前只能读取，用户必须离开工作台才能修改文件。文件计划历史中的“删除”又实际使用 `archived_at` 软归档，执行记录只允许在 `rolled-back` 后删除。用户明确要求在应用内安全编辑源码，并主动取消上述两项状态保护：`applied` 执行记录、`cancelled`/`applied`/已撤销计划及旧归档记录都应能在预览和二次确认后永久清理。

模板源码、撤销备份和历史数据库记录仍是受保护数据。取消状态保护不扩大 Renderer 权限，也不允许历史清理反向改变当前模板工作区。

## 决定

1. 模板源码编辑采用 Main 持有的两阶段预览。Renderer 只提交模板 ID 与 UTF-8 文本请求预览；Main 返回不透明 `previewId`、到期时间、原内容 SHA-256 和可展示的行级变更范围。应用阶段只接受 `previewId` 与 `confirmed: true`。
2. Main 每次预览和应用都从当前活动工作区重新取得模板记录，并复用授权根目录、普通文件、符号链接和越界校验。源码正文与 Diff 不写入日志、错误报告、测试快照或截图文件名。
3. 源文件和新内容都限制为 2 MiB UTF-8 文本；NUL、无效 UTF-8、明显二进制控制字符和超限内容在写入前拒绝。预览后的文件 SHA-256、路径、工作区或模板状态变化会使预览失效，禁止覆盖外部修改。
4. 写入前创建仅供本次事务恢复的受管备份，并在源文件同目录写入新临时文件、同步后原子替换。替换后执行完整工作区扫描与索引发布；稳定模板 ID、元数据和题目关系必须保持。写入、扫描或数据库同步失败时恢复原文件并重新同步索引；补偿失败时保留备份并返回要求停止编辑的可操作错误。
5. 取消编辑、关闭 Diff、过期预览或未提交 `confirmed: true` 均不执行文件写入。成功后 Renderer 刷新源码与工作区快照，继续选中同一模板并保留列表/布局状态。
6. 文件历史删除同样采用“影响预览 + 不透明预览 ID + 显式确认”。执行记录预览同时接受当前工作区的 `applied` 与 `rolled-back`；计划预览接受非草稿的 `cancelled`、`applied`、含已撤销执行的计划以及旧 `archived_at IS NOT NULL` 记录。`draft` 仍须先取消。
7. 删除执行记录会永久删除选中执行行及严格匹配 `file-plan-backups/<execution-uuid>` 的现存专属备份，但保留父计划。删除计划会先枚举全部子执行与备份，再删除子执行和父计划；数据库外键级联只是事务保护，不替代影响枚举。
8. 永久删除不会撤销、恢复、移动、重命名、覆盖或删除当前模板工作区中的任何文件，也不会修改题目、模板元数据或关系。删除 `applied` 记录或计划后，对应的从备份撤销能力永久消失。
9. 批量删除在暂存前一次性校验 UUID 唯一性、活动工作区归属、计划/执行状态、旧归档标记、子记录集合及备份目录格式。未知 ID、跨工作区 ID、重复 ID、草稿或预览后并发变化会拒绝整批。
10. 备份目录缺失作为准确影响结果返回，不阻止删除数据库历史；格式异常、越过 `userData`、符号链接或非目录目标则整批拒绝。Renderer 永远不能提交备份路径。
11. 文件系统与 SQLite 使用现有 `data-management-quarantine/.cleanup-<operation-id>.tmp`、`cleanup-journal.json` `v1` 和内容指纹协议协调。先把现存备份原子移动到暂存区，再在同一 SQLite 事务内删除历史并写入 `file_history_delete_commit:<operation-id>` 提交标记；数据库失败恢复全部暂存项，提交成功后清理暂存区和标记。
12. 数据管理的异常中断恢复识别上述提交标记：无标记的中断清理恢复原备份；有标记的中断清理只完成暂存区删除并清除标记。这样崩溃不会把已提交删除的撤销能力静默恢复，也不会让未提交删除丢失备份。
13. 新的用户可见“删除计划记录”只执行永久删除，不再写入 `archived_at`。字段和旧值保留用于已有 V2 数据兼容；历史管理单独显示旧归档记录和数量，并经同一预览、确认与补偿链永久清理，不通过 migration 静默删除。

## 数据兼容

- 不新增 SQLite 表或列；历史删除提交标记复用 `app_state`，因此不需要 migration。
- `file_change_plans.archived_at` 保留读取兼容，但新操作不再写入。
- 现有全新和已有 V2 userData 原位使用同一 schema；旧归档计划、现有执行记录和备份不会在升级或启动时自动删除。
- `cleanup-journal.json` 继续为 `v1`。新的数据库提交标记只决定中断后恢复方向，不改变 journal 中受管相对路径和内容指纹格式。

## 后果

- 用户获得工作台内源码修改与可审查的永久历史清理能力，同时明确承担删除撤销证据后不可恢复的后果。
- `applied` 不再是执行历史删除的阻止条件；ADR-0019 中“必须先撤销”的决定失效。
- 计划删除不再等同软归档；ADR-0017 中“只隐藏且保留历史/备份”的决定失效。旧 ADR 保留作为历史背景，不改写。
- 永久删除需要文件系统暂存、SQLite 事务和中断恢复协同，复杂度高于原软归档，但当前工作区文件生命周期与历史/撤销证据生命周期保持清晰解耦。
