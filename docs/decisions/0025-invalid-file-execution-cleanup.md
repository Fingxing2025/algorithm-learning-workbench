# ADR-0025：失效文件执行记录清理

- 状态：部分被 ADR-0026 取代
- 日期：2026-07-24

> ADR-0026 已将数据健康和失效执行记录统一收紧为“当前工作区”边界。本文的受控删除、
> 一次性预览、确认复检和只删执行行等安全语义继续有效；“跨全部工作区查询/清理”不再
> 有效。

## 背景

“备份与恢复”的数据健康检查会扫描全部 `file_change_executions`，并把仍为
`applied`、但撤销备份目录已经缺失的记录报告为错误。总体文件 AI 管理的普通执行历史
只读取当前活动工作区，因此失效记录属于其他工作区时会出现“健康检查有 1 项，但 AI
管理没有记录”的不可处理状态。

普通执行历史还仅依据 `status === 'applied'` 公开 `canRollback`，没有验证专属
`file-plan-backups/<execution-id>` 是否存在。缺失备份的记录因此可能继续显示不可完成的
“从备份撤销”。

用户要求为这种失效记录提供受控删除能力。该能力不能演变为 Renderer 可操作的通用
数据库清理器，也不能为了消除诊断而接触当前工作区文件或仍然有效的撤销备份。

## 决定

1. 新增 Main 侧共享失效执行检测器，供数据健康检查和 AI 文件历史共同使用。首个版本只
   把同时满足以下条件的记录标记为可清理：状态为 `applied`；仍通过计划关联到已知 V2
   工作区；`backup_directory` 严格等于 `file-plan-backups/<execution-id>`；对应受管路径
   不存在。
2. `rolled-back` 记录缺少备份是正常状态，不进入失效列表。路径格式异常、符号链接、
   非目录对象、外键错误或其他无法安全判定的数据库问题失败关闭，不提供自动删除。
3. “备份与恢复”只检查当前工作区，并为该问题提供“前往 AI 管理处理”导航。总体文件
   AI 管理只拥有当前工作区的“失效执行记录”列表、选择、预览和确认删除。
4. 失效列表不依赖普通历史分页，但必须由 Main 固定到当前活动工作区。Renderer 只接收执行 UUID、工作区
   UUID/名称、执行时间、可选操作数量和受控原因；不接收备份路径、绝对路径、SQL 或
   数据库筛选条件。
5. 删除使用独立的三阶段命名 API：分页列出、影响预览、按不透明 `previewId` 显式确认。
   预览保存在 Main 内存中，10 分钟过期且一次性消费。
6. 确认前重新验证全部记录仍存在、仍为 `applied`、归属和备份引用未变化、备份目录仍然
   缺失。任一记录或文件状态变化时整批拒绝，不删除任何记录。
7. 合格失效记录的备份目录客观上不存在，确认操作只在一个 SQLite 事务中删除所选
   `file_change_executions` 行并保留父计划。不得调用会移动或删除确认时重新出现备份的
   通用历史删除流程。
8. 删除不会恢复、移动、重命名、覆盖或删除模板、题目、关系、元数据、源码或有效撤销
   备份。不得根据当前文件状态伪造操作前撤销备份。
9. Renderer 默认不选择任何记录；预览和确认文案明确撤销能力已先行丢失、本次只清理
   历史、删除不可恢复且当前文件不会变化。
10. 普通历史中与失效列表重复的执行记录不再显示可用撤销按钮，而显示“撤销备份已缺失”。
11. 本变更使用命名明确、Zod 校验的 `template-management:*` IPC/Preload 白名单，不开放
    原始 IPC。现有 SQLite schema 足够表达删除，不新增表、列或 migration。

## 数据兼容

- 全新 userData 没有失效记录，不显示清理面板，也不发生启动写入。
- 已有 V2 数据只在用户进入页面时只读检查；不会自动删除或迁移。
- 旧 `.awb-backup` 恢复后若重新带回同类记录，可再次通过相同预览和确认流程处理。
- 普通执行/计划永久删除、备份 v1/v2、完整恢复、中断恢复和隔离兼容协议不变。

## 后果

- 数据健康计数与可处理列表使用同一工作区和同一判定；其他工作区记录不会出现在当前
  工作区页面。
- 用户可以删除已经没有实际撤销能力的历史记录，同时保持当前文件和有效备份不变。
- 确认时备份目录重新出现会阻止删除；应用不会在用户只预览“缺失记录清理”后扩大为删除
  一个重新出现的备份目录。
- 其他数据库完整性错误继续由诊断报告，不能借本功能静默清除。
